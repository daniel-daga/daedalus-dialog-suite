## Must fix

1. **P2 — The mocked suite is dead: every file that reaches the fakes fails, and no job runs them**
   (`jest.mocked.config.js:1-15`, `tests/mocks/daedalus-parser-model.ts`,
   `tests/mocks/daedalus-parser-generator.ts`, `package.json:23`, pointed at by
   `jest.config.js:16` and `AGENTS.md:280`)
   - **What this is:** `npm run test:mocked` swaps two `daedalus-parser`
     subpaths for 88 lines of hand-written classes: a 43-line model module and
     a 45-line "generator" whose `generateSemanticModel` returns
     `JSON.stringify(model)` with strings appended for the three condition
     shapes it recognises.
   - **Problem:** it does not work, and nothing would have told anyone. Run
     against the mocked config:
     `tests/CodeGeneratorService.test.ts` **16 failed of 16**,
     `tests/ValidationService.test.ts` **41 of 41**,
     `tests/questConditions.test.ts` 6 of 22, `tests/traderDialogTemplate.test.ts`
     1 of 5 — **64 of 84 tests red**. The dominant cause is one missing export:
     `TypeError: (0, semantic_model_1.deserializeSemanticModel) is not a function`,
     because the fake model module exports 20 classes and the real
     `src/semantic/semantic-model.ts` exports about fifty, including
     `deserializeSemanticModel` and every `deserialize*` helper the two services
     call first. Nothing compares the two lists, so the fake drifts silently and
     the drift is only discovered by running a command nobody runs.
   - **Who it costs:** the contributor `jest.config.js` sends here. Its error
     text is "daedalus-parser is not installed — run `pnpm install`. For the
     mocked suite use `npm run test:mocked`", so on a machine where the native
     parser will not build, the documented fallback is 64 failures. The next
     step from there is to weaken real assertions until it goes green, which is
     how a fake becomes the specification.
   - **Test that does not exist:** none needed. The mocked suite *is* the thing
     without a test — nothing asserts it passes.
   - **Minimal fix:** delete it. `jest.mocked.config.js`, `tests/mocks/`, the
     `test:mocked` script and the `AGENTS.md` row: −110 lines, and the loud
     parser-presence guard in `jest.config.js` becomes the only story about a
     missing parser. If the fallback is genuinely wanted, the smallest thing
     that works is a single test that the fake's export list equals the real
     module's, in the default (real-parser) suite — 6 lines, and it fails the
     day the real model grows a class instead of the day someone tries to use
     the mock.
   - **If we skip it:** a documented command stays broken, and the two fakes
     keep being maintained by hand with nothing comparing them to the thing
     they stand in for.

2. **P2 — Two of the three "pure domain layer" rules have no guard at all, and the one guard cannot see a side-effect import**
   (`tests/questDomainBoundary.test.ts:22-35`, the import regex at `:24`;
   the unguarded rules are `src/renderer/problems/domain/` and
   `src/renderer/simulator/`)
   - **What this is:** `AGENTS.md` states as a hard rule that the three pure
     layers — `src/renderer/quest/domain/`, `src/renderer/problems/domain/` and
     `src/renderer/simulator/` — carry no React/MUI/Electron imports. Only the
     quest tree has a test for it, and that test finds imports by matching
     `/(?:import|export)\s[^'"]*?from\s*['"]([^'"]+)['"]/`.
   - **Problem:** that regex requires a `from` clause. `import 'electron';`,
     `require('electron')` and `await import('electron')` are invisible to it.
     Proven: prepending `import 'electron';` to
     `src/renderer/quest/domain/analysis.ts` leaves the suite **4 of 4 green**.
     And the sibling directories have no test at all — so a problems rule that
     imports `@mui/material` (the most common way this rule is broken, since a
     rule module that starts returning a chip is a natural refactor) breaks the
     documented layering with nothing to notice. They are clean today; the
     guard is what is missing, not the discipline.
   - **Who it costs:** the architecture claim. `docs/architecture/quest-editor.md`
     and `AGENTS.md` say "no React/MUI/Electron imports" as a property of the
     tree; a reader believes it because a test exists. Half of it is not true of
     the test, and two thirds of it is not tested.
   - **Test that does not exist:** the same guard, over
     `src/renderer/problems/domain/` and `src/renderer/simulator/`, with a
     pattern that also matches a bare `import 'x'`, a `require(` and a dynamic
     `import(`.
   - **Minimal fix:** turn `questDomainBoundary.test.ts` into
     `domainBoundary.test.ts` over a list of the three directories, and widen
     the pattern to
     `/(?:\bfrom\s*|\bimport\s*\(?\s*|\brequire\s*\(\s*)['"]([^'"]+)['"]/`.
     ~10 lines, no product code.
   - **If we skip it:** the one rule the repo advertises about its own layering
     is one third enforced and, in the third that is enforced, blind to two of
     the three import forms.

## Should fix

   (`tests/SearchResults.perf.test.tsx:38-56`; the component it claims to guard
   is virtualised at `src/renderer/components/SearchResults.tsx:180-200`)

     results, times the render, and prints two numbers:
     `Render time for 1000 results: …ms` and `Rendered items count: …`. Its own
     comments still say the intent — "Once optimized, this should fail if we

     a whole project (every symbol, every dialog line), and nothing would report
     it going from 40 rows in the DOM to 1,000 — which is a visible stall on

   - **Test that does not exist:** the two lines the comment describes.
   - **Minimal fix:** `expect(items.length).toBeLessThan(50);` after the count,
     and drop the timing `console.log` (a logged duration is not a guard, and it

     it or fold it into `DialogTree.test.tsx`.
   - **If we skip it:** a perf suite that reports numbers and guards nothing is
     worse than no suite, because its name counts as coverage.

4. **P3 — The fake main process drops `expectedVersion`, so no browser-harness spec can ever see a write refused**
   (`src/renderer/utils/mockAPI.ts:491-500` `writeFile`, `:621-639` `saveFile`;
   the product side is `src/renderer/store/fileStore.ts:837` and `:863`,
   `src/renderer/store/projectStore.ts:481`)
   - **What this is:** `EditorAPI.writeFile` takes a third argument —
     `options?: { expectedVersion?: string }` — and `EditorAPI.saveFile` takes a
     fourth carrying the same; both mean "write only if the file on disk is
     still the bytes I read". The mock declares two and three parameters
     respectively and ignores the rest.
   - **Problem:** two consequences, both invisible. First, the guard itself never
     runs in the harness, so a regression that stopped passing
     `expectedVersion` — or one that made the main process write blindly — is
     undetectable in the only suite that drives the real renderer's save flow
     against a fake backend. Second, the fake's `saveFile` returns
     `{ success: true, validationResult }` with **no `version`**, so
     `fileStore.ts:863`'s `currentFileState.diskVersion = result.version` stores
     `undefined` after the first harness save; every save after that sends
     `expectedVersion: undefined`, which the real handler correctly reads as "no
     expectation". A harness that cannot express the refusal cannot test it, and
     a save chain that silently loses its baseline is the shape of a stale-write
     bug. `tests/fixtures/` and `fileStore.diskVersion.test.ts` are unaffected —
     they stub both ends explicitly, which is why this is not a data-loss hole
     today.
   - **Who it costs:** nobody yet. The cost is the coverage: the version guard
     is one of the few places where the editor writes to a file it did not
     create, and the browser harness — where all 48 UI-flow specs live — cannot
     reach it.
   - **Test that does not exist:** `mockAPI.readFileVersioned` should mint a
     version over the bytes *and* a counter that changes on write, `writeFile`/
     `saveFile` should compare it and return `{ success: false, error: … }` on a
     mismatch, and the fake's successful save should return the version it
     wrote. Then one spec: edit, save, inject an external change of the same
     length through `__mockEmitFileChange`, save again, expect the refusal
     surfaced.
   - **Minimal fix:** in `writeFile`/`saveFile`, accept the options argument and
     honour it against a version the fake keeps per path (`mockapi_version_…`,
     a counter bumped on every write); return the new version from `saveFile`.
     ~12 lines in the two helpers both already share, no product code.
   - **If we skip it:** the harness keeps proving the renderer *calls* save and
     never that a save is refused, and `diskVersion` keeps being `undefined`
     after the first save in every harness flow.

5. **P3 — `tests/searchablePaneDesign.test.tsx` asserts a `data-ui-pattern` attribute that nothing else in the repo reads**
   (`tests/searchablePaneDesign.test.tsx:11`, `:80`; the attribute is set by
   `src/renderer/components/QuestList.tsx:194`, `NPCList.tsx:96`,
   `DialogTree.tsx:289`, `SearchPanel.tsx:65`, `VariableManager.tsx:148`,
   `Problems/ProblemsPanel.tsx:156` from
   `src/renderer/components/common/searchablePaneStyles.ts:4`)
   - **What this is:** five tests, each rendering a pane and asserting the root
     carries `data-ui-pattern="searchable-pane-v1"`.
   - **Problem:** the attribute is a self-declaration. No CSS, no spec and no
     other code selects on it — the only reader in the repository is this test.
     So it asserts that a string the component writes is present, which is
     exactly the shape of a test that exists for coverage. What the "design
     language" actually is — `searchablePaneShellSx`, `searchablePaneHeaderSx`,
     `searchablePaneRowButtonSx` — is not asserted anywhere. Proven: replacing
     `QuestList.tsx:195`'s `...searchablePaneShellSx(theme)` with a literal
     `{ bgcolor: 'hotpink', height: '100%', … }`, leaving the marker in place,
     keeps the suite **5 of 5 green**. A pane can leave the shared design
     language entirely and the suite that exists to prevent that cannot see it.
   - **Who it costs:** the consistency the attribute stands for. Five panes that
     all claim the same pattern while looking different is worse than no marker,
     because a reader trusts the assertion.
   - **Test that does not exist:** either one that fails when a pane stops using
     the shared `sx` helpers (render and compare a computed style, or assert the
     `sx` result by hand), or nothing.
   - **Minimal fix:** delete `tests/searchablePaneDesign.test.tsx` and the
     attribute with it (−150 lines and six one-line edits), or keep the
     attribute and add one real assertion per pane against the shared shell
     helper. Deleting is the honest half of the choice: 150 lines that assert a
     marker nobody consumes are 150 lines that will be updated reflexively
     whenever a pane changes and will never once have caught a defect.
   - **If we skip it:** a suite that reads as "the panes share a design language"
     keeps passing while they do not.

6. **P3 — `windowSecurity.test.ts`'s dev-server case cannot tell an origin check from a prefix check**
   (`tests/windowSecurity.test.ts:66-77`; the rule under test is
   `src/main/windowSecurity.ts:14-16`)
   - **What this is:** in development, navigation is allowed when
     `url.startsWith('http://localhost:5173')`. The test's positive case is
     `http://localhost:5173/index.html` and its negative case is
     `https://evil.example.com`.
   - **Problem:** neither URL can distinguish "this origin" from "this string
     prefix". Proven: widening the rule to `url.startsWith('http://localhost')`
     — every port, every dev server on the machine — leaves
     `windowSecurity.test.ts` **4 of 4 green**, including the test named "allows
     the dev server URL only in development". The shipped rule has the same
     shape in the other direction and today allows
     `http://localhost:5173.evil.example`, which a clicked link would reach.
     This is development-only, which is why it is not higher: in a release build
     the branch is `url === webContents.getURL()` and the tests do cover that.
   - **Who it costs:** a developer running the dev server, who is one crafted
     link from a page that looks like the app. Small, but the guard's whole job
     is to hold when nobody is looking.
   - **Test that does not exist:** one negative case per branch —
     `http://localhost:5173.evil.example`, `http://localhost:5174/`,
     `https://localhost:5173/`.
   - **Minimal fix:** those three lines in the test, and `new URL(url).origin ===
     'http://localhost:5173'` in `windowSecurity.ts` (2 lines, keeps the
     behaviour the test expects and makes the URL shapes above fail).
   - **If we skip it:** the navigation guard's weakest branch is the one with a
     test that cannot fail.

7. **P3 — The fake's change and close channels hold exactly one listener, and any unsubscribe closes the channel for everyone**
   (`src/renderer/utils/mockAPI.ts:15`, `:21`, `:842-848`, `:865-871`; the real
   thing is `src/main/preload.ts:50-55`)
   - **What this is:** `onFileChanged` and `onCloseRequested` each store their
     callback in a module-level `let`, overwriting whatever was there, and their
     returned unsubscribe sets it to `null` regardless of which callback
     unsubscribed.
   - **Problem:** the real preload registers a fresh `ipcRenderer.on` listener
     per call and removes only its own on unsubscribe, so the app may have any
     number of subscribers. The fake therefore fails in two silent directions: a
     second subscriber gets nothing and the spec's injected event reaches only
     the most recent one; and when any subscriber unmounts, the channel goes
     dead for the survivor. Today `useFileWatcher()` is mounted once
     (`App.tsx:106`), so no spec is wrong — this is a fake that is right by
     accident, and the accident is what a second subscriber removes. The
     close-guard and external-conflict specs would then be green while testing
     nobody's handler.
   - **Who it costs:** the next person who subscribes — the level editor already
     has a second reason to want file-change events.
   - **Test that does not exist:** one spec-adjacent Jest test on the mock
     itself: subscribe twice, inject once, both callbacks fire; unsubscribe one,
     the other still fires. Three lines of `Set` in the mock.
   - **Minimal fix:** replace the two module-level `let`s with `Set`s — add on
     subscribe, delete that one on unsubscribe, iterate on emit. ~8 lines
     removed from what is there.
   - **If we skip it:** the two hooks the harness uses to fake the two events the
     real app cannot otherwise produce will quietly serve one listener each,
     with nothing to say so.

## Verdict

Verdict: fix 1 and 2 first. Finding 1 is a documented command that no longer
works and has no gate, so its next 64 failures will be met by someone with no
reason to trust them; deleting it is cheaper and more honest than repairing a
hand-written copy of a parser model. Finding 2 is the same class one level up:
an architecture rule the repo states in `AGENTS.md` with one third of it tested
and that third blind to two import forms. Findings 3 through 7 are each a test
that stays green when the thing it names is broken — proven by mutation, not
argued — and each fix is a handful of lines with no product code behind it
except 6's two-line origin check. Nothing here is a P1: no user loses data
because of this slice, and the Jest suite that does pin the save guard
(`fileStore.diskVersion.test.ts`) is well built. The defect is in what a green
run is allowed to mean.

Lean: −260 lines possible. Deleting `jest.mocked.config.js`, `tests/mocks/` and
the `test:mocked` script is −110; deleting `searchablePaneDesign.test.tsx` and
its six attribute writes is −150; the rest of the findings are net-neutral or
add a dozen lines each.

Not checked: I did not run the full Jest or Playwright suites, launch the app,
or run the Windows stability matrix, so "these 40 suites do real work" is
sampled (about thirty read in full, chosen for their names) rather than
measured. I did not run `npm run test:mocked` in full — only the four files that
reach the fakes, which is where every failure I report comes from; there may be
more elsewhere. Findings 3, 5 and 6 are mutation evidence on a loaded-free
machine; on a slower runner the timing numbers in finding 3 drift, which does
not change the conclusion because nothing asserts them.
